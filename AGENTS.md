# Repository Guidelines

## Project Structure & Module Organization

This repository is GitOps infrastructure for Talos and Kubernetes.
All cluster or platform changes must be made through code in this repository; avoid manual in-cluster drift.

- `kubernetes/flux/cluster/`: Flux entrypoint and top-level reconciliation scope.
- `kubernetes/apps/`: application stacks grouped by domain/namespace.
- `kubernetes/components/`: reusable shared resources (alerts, volsync, etc.).
- `talos/`: Talos cluster config for topf (`topf.yaml`, `secrets.sops.yaml`) with patch directories (`all/`, `control-plane/`, `worker/`).
- `bootstrap/`: initial bootstrap resources, Helmfile layers, and encrypted secrets.
- `.taskfiles/` + `Taskfile.yaml`: operational tasks for Talos/bootstrap/reconcile flows.
- `util/`: small operational checks (for example drift detection).

## How `kubernetes/apps` Kustomizations Work

- Flux starts from `kubernetes/flux/cluster/ks.yaml` (`Kustomization/cluster-apps`) with `spec.path: ./kubernetes/apps`.
- `cluster-apps` applies defaults to every child Flux `Kustomization` via `spec.patches` (notably `deletionPolicy: WaitForTermination` and HelmRelease install/upgrade/rollback remediation defaults).
- Each namespace/domain folder (`kubernetes/apps/<namespace>/kustomization.yaml`) is a **Kustomize config** that:
    - sets `namespace: <namespace>`
    - includes shared `../../components/alerts`
    - includes `./namespace.yaml` and one or more app `./<app>/ks.yaml` entries
- Each app `ks.yaml` is a **Flux Kustomization CR** (or multiple CRs) that points to a concrete manifest path such as `./kubernetes/apps/<namespace>/<app>/app` and usually sets:
    - `sourceRef: GitRepository/flux-system`
    - `targetNamespace: <namespace>`
    - optional `dependsOn`, `healthChecks`, `healthCheckExprs`, and `wait`
- Each app manifest path (`app/`, `instance/`, `cluster/`, `common/`, etc.) contains a `kustomization.yaml` that is standard Kustomize resource composition (`helmrelease.yaml`, `ocirepository.yaml`, `externalsecret.yaml`, routes, policies, etc.; app-template apps get their `OCIRepository` from `components/app-template` at the namespace layer).
- `namespace.yaml` files use `metadata.name: _`; the parent namespace Kustomize layer sets the real namespace name.

When adding or changing apps under `kubernetes/apps`, preserve this three-layer model:

1. Namespace-level `kustomization.yaml` wires namespace + app `ks.yaml` entries.
2. App-level `ks.yaml` defines Flux reconciliation behavior and ordering.
3. App subdirectory `kustomization.yaml` defines the actual Kubernetes manifests.

## Build, Test, and Development Commands

Use `mise` to install pinned tooling from `.mise.toml`, then run:

- `task --list`: list all available tasks.
- `task talos:generate-config`: generate Talos cluster configuration.
- `task bootstrap:full`: run the full Talos + Kubernetes bootstrap sequence.
- `task reconcile`: force Flux to reconcile from Git.
- `bash util/check_drift_detection.sh`: verify global `cluster-apps` drift detection patch and fail on per-app leftovers.

## Coding Style & Naming Conventions

The repo is YAML-heavy and declarative.

- Follow `.editorconfig`: 2-space indentation by default, LF endings, final newline.
- `*.md` and `*.sh` use 4-space indentation.
- Keep file names lowercase and hyphenated; use common manifest names like `kustomization.yaml`, `helmrelease.yaml`, and `externalsecret.yaml`.
- Format YAML, JSON, and Markdown documents using `oxfmt` via `lefthook`.
- Standardize container runtime IDs on `1000:1000` (`runAsUser`, `runAsGroup`, `fsGroup`, and `PUID`/`PGID`) unless an image has a hard requirement for a different UID/GID.
- Prefer `https://k8s-schemas.home-operations.com/` for Kubernetes and CRD `yaml-language-server` schema URLs wherever that site serves the needed schema; only fall back to other schema sources when no equivalent exists (e.g. `json.schemastore.org/kustomization` for Kustomize configs). The retired `kubernetes-schemas.brauni.dev` mirror must not be referenced anymore.
- Always pin container images by digest (`@sha256:...`). Do not use unpinned image references.

## App Exposure Rule

- If an app has a URL and a web UI, always create a `DNSEndpoint` manifest and include it in that app's `kustomization.yaml`.
- If an app has a URL and a web UI, expose it in Homepage via `gethomepage.dev/*` annotations on the app's route/ingress resources; do not add static service entries in `kubernetes/apps/selfhosted/homepage/app/configuration.yaml`.

## Upstream Template Preference

- Prefer implementations that stay as close as possible to upstream patterns used in local template repos `./tmp/bjw-s` and `./tmp/onedr0p`.
- When adding or changing apps/features in this repo, use those two repos as primary structural and naming references unless this repository has an explicit conflicting requirement.
- Common expected adaptations from those upstream templates in this repo:
    - URLs and domains.
    - Password/secret source: use Infisical ExternalSecrets instead of 1Password/Bitwarden equivalents.
    - Envoy names.

## Secrets Management with Infisical

This repo uses Infisical (EU region) as the central secret store, accessed via external-secrets-operator.

### ClusterSecretStore

- **Name:** `infisical`
- **Location:** `kubernetes/apps/external-secrets/external-secrets/infisical/clustersecretstore.yaml`
- **Host:** `https://eu.infisical.com`
- **Project:** `ovh-ops-u1ua`, environment `prod`
- **Auth:** Universal Auth credentials bootstrapped from `bootstrap/secrets.sops.yaml`

### Secret Path Convention

Secrets are organized by app folder: `/<app-name>/SECRET_NAME`. Common paths:

- `/authentik/` — Authentik identity provider
- `/cloudnative-pg/` — Per-app PostgreSQL credentials (for example `/cloudnative-pg/sonarr_postgres_username`)
- `/servarr/` — Shared API key for Sonarr/Radarr/Prowlarr. Only apps that pass the key straight to an env var consume the shared `media/servarr-secret` (`servarr` ExternalSecret, key `API_KEY`); apps that template config files from it (`bazarr`, `bazarr4k`, `warrden`) keep their own ExternalSecret because ESO templates cannot read another Secret.
- `/volsync-template/` — Kopia backup repository credentials
- `/rclone/` — Rclone remote mount credentials
- `/<app>/` — App-specific secrets

### ExternalSecret Pattern

When adding an app that needs secrets, create `externalsecret.yaml` following this template:

```yaml
---
# yaml-language-server: $schema=https://k8s-schemas.home-operations.com/external-secrets.io/externalsecret_v1.json
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
    name: <app>
spec:
    refreshInterval: 12h
    secretStoreRef:
        kind: ClusterSecretStore
        name: infisical
    target:
        name: <app>-secret
        creationPolicy: Owner
        template:
            engineVersion: v2
            data:
                ENV_VAR_NAME: "{{ .SECRET_KEY }}"
    data:
        - secretKey: SECRET_KEY
          remoteRef:
              key: /<app>/SECRET_NAME
```

### Flux Dependency

Apps using Infisical secrets must declare the dependency in their `ks.yaml`:

```yaml
spec:
    dependsOn:
        - name: infisical
```

### Reusable Components

The shared `kubernetes/components/cnpg` component uses variable substitution (`${APP}`) to pull per-app PostgreSQL credentials from `/cloudnative-pg/${APP}_postgres_username` and `/cloudnative-pg/${APP}_postgres_password`.

To rotate: `ceph auth rotate client.rgw.proxmox.s3.a --key-type=aes256k` on the Proxmox host, patch the k8s Secret's `keyring` field with the new key (same keyring format, caps preserved), then `rollout restart deploy/rook-ceph-rgw-proxmox-s3-a`. - external-dns v0.22.0 (chart 1.22.0, Renovate PR #1175, 2026-09-13) broke `--annotation-filter` on the CRD source: the filter is parsed via `metav1.ParseToLabelSelector` (`source/annotations/processors.go`) which rejects set-based selectors, the error is discarded in `NewSourceConfig`, and the resulting selector matches **nothing** in the informer transform — every DNSEndpoint is dropped from the cache. With `policy: sync` the very first sync after the upgrade mass-**deleted** every `ovh-ops.*`-owned record in the Cloudflare zones `480p.com` (all records) and `brauni.dev` (all external-dns records); `riki.boo` survived only because its records were still owned under the older `k8s.cname-*` TXT prefix. Until upstream fixes annotation-filter parsing on the CRD source, do NOT switch these HelmReleases back to `--annotation-filter`, and treat any external-dns upgrade as potentially record-deleting: verify sources with a `--dry-run --once` one-off pod (`kubectl run` with the same args) before letting a new version reconcile. Restored 2026-09-13 by recreating records via the label-filter config; leftover unowned `k8s.cname-*` TXT records plus their unowned CNAMEs still exist in `riki.boo` and are skipped by the `ovh-ops.`-prefixed instance (cosmetic; clean up by deleting them and letting external-dns recreate owned copies).
- For multi-domain TinyAuth protection, this repo uses separate `HTTPRoute` objects per hostname/domain and then attaches a matching `SecurityPolicy` to each route. Do not assume a single generated route can be targeted per-host with `sectionName`; follow patterns like `kubernetes/apps/network/echo/app/httproute.yaml` and `kubernetes/apps/network/echo/app/securitypolicy.yaml`.
- For apps exposed with a web UI, prefer annotation-driven Homepage discovery (`gethomepage.dev/*`) on route/ingress resources plus a `DNSEndpoint`; do not rely on static Homepage `services.yaml` entries.
- app-template v5 defaults `defaultPodOptions.automountServiceAccountToken` to `false`; apps/sidecars that call the Kubernetes API (for example Gatus sidecar and Homepage discovery) must explicitly set it to `true` or mount a projected token.
- The shared CNPG component in `kubernetes/components/cnpg` creates the usual `${APP}-initdb-secret` and `${APP}-pguser-secret` flow and defaults to a single database named `${APP}`. Apps that can tolerate a single DB should prefer that standard path.
- CNPG cluster backups in `kubernetes/apps/dbms/cloudnative-pg/cluster` now use `ScheduledBackup.spec.method: barmanObjectStore` with the `cnpg-backups` ObjectBucketClaim/secret; do not reintroduce VolumeSnapshot or VolSync resources just to enable routine backups.
- When bootstrapping a replacement CNPG cluster from an object-store backup while keeping backup archiving enabled, do not point the new cluster at the same Barman archive path/server lineage as the source backup. Use a fresh backup destination (for example `.../v2/`) or another unique server name, otherwise recovery can fail with `Expected empty archive` during the WAL archive safety check.
- For media namespace remote mounts, this repo uses rclone sidecar containers co-located in each app pod (not a separate CSI driver). The sidecar runs `rclone mount` with `Bidirectional` mount propagation on a host `/tmp` path; the app container picks up the mount via `HostToContainer` propagation. This ties the mount lifecycle directly to the app pod: app restart → mounts restart, and mount failures surface as sidecar probe failures that block the pod. See `kubernetes/apps/media/sonarr/app/helmrelease.yaml` or `kubernetes/apps/media/media-debug/app/helmrelease.yaml` for the canonical pattern.
- Sonarr in this repo is intended to use native Postgres env configuration with the `home-operations/sonarr` image. The working pattern is to set `SONARR__POSTGRES__*` env vars from `sonarr-pguser-secret` and disable the separate log database with `SONARR__LOG__DBENABLED: "False"` so logs stay on disk/Loki.
- Large VolSync Kopia restores in this repo can exceed the default cache EmptyDir size and get evicted with `Usage of EmptyDir volume "cache" exceeds the limit`. The shared `kubernetes/components/volsync/replicationdestination.yaml` should keep a larger `spec.kopia.cacheCapacity` (currently `32Gi`) unless an app has a smaller proven requirement.
- **volsync → kopiur migration (in progress)**: `kopiur-system/kopiur` runs the home-operations kopiur operator; `ClusterRepository/sftp` **adopts** the same kopia SFTP repository the perfectra1n volsync fork wrote to (no `create` block — it can never format a fresh repo over the history). Two hard requirements learned the hard way: (1) the chart flag `features.credentialProjection.enabled: true` MUST be set — the operator's `secrets` create/patch/delete RBAC is gated on it (necessarily unscoped; `create` cannot be resourceName-scoped), and without it every mover Job 403s with a `MissingDependency` naming the flag; (2) adopting the fork's repo requires pinning `sources[0].sourcePathOverride: /data` on every SnapshotPolicy — kopiur's default source path is `/pvc/<name>`, so without the pin the history silently forks and `fromPolicy` restores come up empty. `identityDefaults` (`hostnameExpr: namespace`, `usernameExpr: policyName`) reproduce the fork's `<app>@<namespace>` identity (same as kopiur's bare defaults). Migrated apps set `KOPIUR_ON_MISSING_SNAPSHOT: Fail` (fail-closed DR); greenfield keeps the `Continue` deploy-or-restore default. The SFTP host/port/username stay out of Git via Flux `postBuild.substituteFrom` on `kopiur-sftp-config` — that ExternalSecret MUST live in the operator Kustomization, NOT in the Kustomization whose postBuild consumes it: Flux resolves substitution at build time, before anything is applied, so a same-Kustomization producer deadlocks `BuildFailed` forever. Credentials (`KOPIA_SFTP_KEY_DATA`/`KOPIA_SFTP_KNOWN_HOSTS`/`KOPIA_PASSWORD`) live in `kopiur-repository` and are **projected** into consumer namespaces — the kopiur component needs NO per-app ExternalSecret, unlike the volsync one. When the last app is migrated: remove the fork's leftover admission policies (`volsync-kopia-maint-keyfile` is already gone; keep `volsync-mover-jitter`/`volsync-pgdump-rw-rootfs` until then), then the volsync operator/CRDs — the Infisical `/volsync-template/*` + `/kopia_known_hosts/*` values stay (kopiur-repository consumes them).

- Talos config generation was migrated from talhelper (archived) to topf (postfinance/topf) in 2026-09, following onedr0p/cluster-template's structure: `topf.yaml` + `secretsPath: secrets.sops.yaml` + per-node `data:` consumed by Go-templated `.yaml.tpl` patches instead of `node/<host>/` directories. Notes: (1) a 1.14-format config is rejected by 1.13 nodes (`"UnattendedInstallConfig": not registered`), so the Talos upgrade must complete before `topf apply` converges the migrated config; (2) `topf`'s 1.14 base does NOT disable kube-proxy (its 1.13 base did) — `control-plane/00-cluster.yaml` must keep `KubeProxyConfig enabled: false` for the Cilium kube-proxy replacement; (3) `machine.kubelet.disableManifestsDirectory` has no typed-config equivalent and was dropped (cluster-template does the same); (4) `SecurityProfileConfig workloadIsolation: false` is pinned explicitly because topf's 1.14 base defaults to `true`, which would break KubeVirt/Rook/node-exporter host access.

Same reasoning as kube-proxy: Talos must not reconcile deployments it does not own.

After fixing the underlying cause, retrigger with `kubectl -n system-upgrade annotate kubernetesupgrade kubernetes tuppr.home-operations.com/reset="$(date)"` (same for `talosupgrade`); the re-run is a no-op fast-path when the actual node work already completed.

Musl/libpq clients (for example `ghcr.io/home-operations/postgres-init`) can treat the failed IPv6 lookup as full hostname resolution failure and stay stuck waiting for PostgreSQL. That rule presumes a public Envoy route on `brauni.dev`; apps exposed solely through the tailscale-operator get their name from MagicDNS and have no public route to annotate. - Kubernetes/CRD schemas come from the shared upstream mirror `k8s-schemas.home-operations.com` (generated from pinned upstream CRD releases plus core kinds extracted from a kind cluster's OpenAPI; new CRDs are added by opening a `sources/<owner>/<repo>/vendir.yml` PR in `home-operations/k8s-schemas`). - VMs live in the `vms` namespace (`kubernetes/apps/vms/`), one Flux Kustomization per VM following the same three-layer model as apps. The namespace must keep `pod-security.kubernetes.io/enforce: privileged` because both `virt-launcher` and the CDI importer pods need it. A VM Kustomization's `healthCheckExprs` on `status.ready` legitimately fails during CDI import; set `retryInterval: 1m` so it self-heals instead of waiting out the full interval. The `smoke-test` Alpine VM (`kubernetes/apps/vms/smoke-test/`) exists to validate the platform end to end — including a 5-second PreCopy live migration between workers — and should be removed once Hermes is settled on a VM.
- KubeVirt uses `spec.domain.firmware.uuid` as the cloud-init `instance-id` (`cloudInitUUIDFromVMI` in `pkg/cloud-init/cloud-init.go`). If a VM has a `firmware` block without an explicit `uuid`, virt-api pins a generated one, every restart reuses the same instance-id, and cloud-init silently skips all per-instance modules (users, ssh keys, packages, runcmd) — changed user-data never applies. Always set `firmware.uuid` explicitly and bump it to a fresh UUID whenever cloud-init user-data changes. Symptom seen here: hostname from meta-data applied, ssh key rejected, no `AgentConnected` condition, while the same image + noCloud.iso boots correctly under local qemu from a fresh disk.
- Guests with masquerade networking are reached through the virt-launcher pod IP (inbound DNAT to 10.0.2.15). `virtctl ssh`'s embedded golang ssh client rejects valid keys where the real `ssh` binary succeeds — use `kubectl port-forward` to the launcher pod (or a Service selecting `kubevirt.io/domain: <vm>`) plus the real ssh client instead. The cluster pod network is IPv4-only, so guests get no routable IPv6 (only `fec0::` site-local auto-addrs); use Tailscale inside a guest if tailnet v6 is needed.
- KubeVirt and CDI are installed from their vendored upstream operator manifests under `kubernetes/apps/kubevirt` and `kubernetes/apps/cdi`; there is no official upstream Helm chart. Runtime images are overridden with digest-pinned operator environment variables. When Renovate bumps only the component images (`operator/images.yaml`), the vendored RBAC can lag the operator version: a new KubeVirt minor may grant itself permissions its own vendored ClusterRole does not hold (e.g. v1.9.0 introduced `plugin.kubevirt.io`), and the API server's RBAC escalation guard then rejects the update with `is forbidden: ... attempting to grant RBAC permissions not currently held`, stalling the upgrade as `DeploymentFailed`. Fix by re-vendoring `operator.yaml` from the matching upstream release (drop the leading Namespace doc, keep the vendored-from header, format with `oxfmt`); a version mismatch between the vendored file header and the image env vars is the tell-tale sign. - OIDC client apps (as opposed to forward-auth ones) get their own blueprint file, `kubernetes/apps/authentik/authentik/app/blueprints/silo-oidc.yaml`: they are **not** proxy providers, so nothing is added to the embedded outpost's provider list and the app's HTTPRoutes get no `SecurityPolicy` — the app validates the ID token itself. Two 2026.8 facts that bite: `redirect_uris` is a **list of objects** (`[{url, matching_mode: strict|regex}]`, stored in the model's `_redirect_uris`), not the old space-separated string; and the blueprint importer runs every entry through the model's API serializer, so API field names apply (`!Find`/`!KeyOf` resolve pks for `signing_key`, `property_mappings`, `authorization_flow`). An OAuth2 provider created without `property_mappings` issues an empty ID token, so reference the three default mappings explicitly — `authentik default OAuth Mapping: OpenID 'openid'/'email'/'profile'`; the `profile` one already emits `groups`, `preferred_username`, `name` and `picture`, which is exactly what Silo's `silo.auth.oidc` plugin reads. **`grant_types` has the same trap and a nastier symptom**: its model default is an empty list (only the admin wizard fills in `authorization_code`/`refresh_token`), and with no grant types the authorize endpoint accepts the client and matches the redirect URI but bounces back `error=invalid_request` / `Invalid grant_type for provider` — which reads like a broken redirect URI while the real cause is one missing attr. Always set both `grant_types` and `property_mappings` on a blueprint-created OAuth2 provider. **Silo has two callback paths**, and the regex must cover both: the current web app runs its handshake on `/api/v2/auth/oauth/<id>/callback` while v1 routes and the apps still use `/api/v1/auth/oauth/<id>/callback`, so anchor on `api/v[12]/auth/oauth/[0-9]+/callback`. Matching only v1 passes a `curl` against the v1 init endpoint but fails the browser round trip with authentik's "Redirect URI Error" (`cause=redirect_uri_no_match` in the server log, next to the offending request). **`policybinding` identifiers include the group**, so _changing_ which group protects an app creates a second binding instead of moving the first — the old group keeps granting access and the app silently stays open to it. Pair the new binding with a `state: absent` entry naming the old `{target, group, order}` triple; it is a no-op once the stale row is gone (verify with `select ... from authentik_policies_policybinding b join authentik_core_group g ... where a.slug='<app>'`, which should list exactly one group). **Access scope belongs in its own group**: binding a client app to `Media` means "can use Silo" and "can use the whole media stack" become the same permission in both directions, so each client app gets a dedicated group (`Silo`) declared in `forward-auth.yaml` with the other groups/users — list attrs there are replaced wholesale, so membership must be declared in that one file rather than split across blueprints. Without a `signing_key` authentik signs HS256 and clients need `allow_hs256`. Validate a blueprint before merging by piping it into the worker and running `Importer.from_string(...).validate()` under `ak shell` (it applies inside a rolled-back transaction); `ak apply_blueprint` refuses arbitrary paths, so `kubectl cp` + `/tmp` + `ak apply_blueprint` does not work.

- The *arr builds here (sonarr/sonarr4k `5.0.0.2742`, prowlarr `2.10.1`) ship Servarr's `AllowedHostsCheck` health warning when `AllowedHosts` is empty and `AuthenticationRequired` is not `Enabled`; the Radarr images predate the check entirely (no key in `config.xml`, no warning). Fix is `SONARR__SERVER__ALLOWEDHOSTS` / `PROWLARR__SERVER__ALLOWEDHOSTS` = `<public-host>,<app>.media.svc.cluster.local`, and then **every** `httpGet` probe needs `httpHeaders: [{name: Host, value: <app>.media.svc.cluster.local}]` — kubelet sends `Host: <podIP>:<port>` and the filter answers it with 400, so probes without the override put the pod in a restart loop. Verified against the live image: allowed names → 200/302, pod IP and unknown hosts → 400, loopback (`Host: localhost`) still allowed. Flipping `AUTH__REQUIRED: Enabled` only _silences_ the health check while `AUTH__METHOD: External` is in play (tested: still `200` for `Host: evil.example.com`) — cosmetic, not a fix.
- `media/infinidysk-sync-helper` (added 2026-10-22) is the manual-NZB (`category=other`) import step that replaces `media/zurg-sync-helper` and `media/altmount-sync-helper` (both retired). A busybox poller with a **read-only** `rclone-infinidysk` sidecar (`--links`, `--read-only`, VFS cache off — it only walks `completed-symlinks/` and reads link targets) and the `symlinks` PVC: for every SAB history slot with `status: Completed` it recreates the release's symlinks under `/aio/symlinks/other/` and clears the job with `del_files=0`. Facts that bite: **(1)** clearing the history entry also removes `completed-symlinks/<category>/<release>` (verified live 2026-10-22), so the farm copy is created and every link verified to resolve _before_ the clear — the farm link is what keeps the release library-linked for health/repair and out of Remove Orphaned Files; **(2)** `mode=history` ignores `limit` because `api.ignore-history-limit` is on, so every slot must be processed — polling only the newest one stalls behind a Downloading item; **(3)** the slots arrive as one compact `},{`-joined line and a `read` loop over a split without a terminating newline silently drops the last (newest) slot — 33 slots parsed as 32 and the newest upload was never placed until the file got `echo >>`; **(4)** `DRY_RUN=1` / `CLEAR_JOBS=0` place links without touching history (first run against an untrusted backend), and a farm copy that is short or has a non-resolving link is removed and retried while its job stays; **(5)** its ingress (3000 + 8080) lives in `media/infinidysk/app/ciliumnetworkpolicy.yaml` like every other consumer, and it is allowlisted in both `util/check_security_invariants.sh` lists. **(6)** after a pass that placed something it also refreshes Jellyfin's `Other` library (`POST /Items/<id>/Refresh?Recursive=true`, library id resolved by name from `/Library/MediaFolders` at runtime) — the counterpart of altmount's Plex section refresh. `POST /Library/Media/Updated` is a 204 no-op for that library because `EnableRealtimeMonitor` is off in its `options.xml`, and Jellyfin 12 accepts only `Authorization: MediaBrowser Token="<key>"` (`X-Emby-Token` and `?api_key=` are 401). The token is `/jellyfin/API_KEY` in Infisical (admin-scoped, deliberately not zurg's push key so Phase 6 can delete `/zurg/*`), and a failed refresh is a WARN that never blocks placement.
